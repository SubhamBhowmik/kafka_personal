# Kafka Producer ⭐⭐⭐⭐⭐

The Kafka Producer is one of the most important Kafka concepts asked in interviews. A **producer** is responsible for publishing (writing) records to Kafka topics.

---

## Producer — Definition

A **Producer** is a client application that sends (publishes) messages/events to one or more Kafka topics.

**Examples:**
- Payment Service → Sends payment events.
- Order Service → Sends order events.
- Notification Service → Sends notification events.

```
Producer
   │
   ▼
+----------------+
|  Kafka Topic   |
+----------------+
```

### Why do we need a Producer?

- Publish events asynchronously.
- High throughput.
- Fault tolerant.
- Scalable.
- Reliable delivery.

### Interview Notes

- Producer **only** writes data.
- Consumer **only** reads data.
- Producer never directly communicates with consumers.

### Tricky Interview Questions

#### Q1. Can one producer write to multiple topics?

**Answer:** Yes. One producer instance can send records to any number of topics.

#### Q2. Does the producer store data permanently?

**Answer:** No. Kafka brokers store the data. The producer only sends it.

---

## Producer Architecture

**Producer Architecture** is the internal workflow Kafka follows before a message reaches the broker.

```
Application
      │
      ▼
KafkaProducer API
      │
      ▼
  Serializer
      │
      ▼
  Partitioner
      │
      ▼
RecordAccumulator
  (Batching)
      │
      ▼
Sender Thread
      │
      ▼
    Broker
```

### Components

#### 1. Application
Creates the message.

```
Order Created
```

#### 2. Serializer
Converts Java object into bytes.

```
Order Object → JSON → Bytes
```

> Kafka only sends bytes.

#### 3. Partitioner
Chooses which partition should receive the record.

**Example:**
```
Topic
 P0   P1   P2

Key = 101 → Always hashes to the same partition.
```

#### 4. Record Accumulator
Temporarily stores messages before sending them.

```
Instead of:  100 records → 100 requests
With batching: 100 records → 1 request
```

Kafka waits and sends many together.

#### 5. Sender Thread
Background thread responsible for actually sending data to brokers.

> Application thread never sends data directly.

### Tricky Interview Questions

#### Q1. Which thread actually sends records?

**Answer:** The **Sender Thread**, not the application thread.

#### Q2. Why doesn't Kafka send immediately after `send()`?

**Answer:** Because it batches records for higher throughput.

## KafkaProducer API

**KafkaProducer** is the Java client used to send records to Kafka.

**Example:**
```java
Producer<String, String> producer =
    new KafkaProducer<>(properties);

producer.send(
    new ProducerRecord<>("orders", "101", "Laptop")
);
```

### Important Methods

#### `send()`
Sends record asynchronously.

```java
producer.send(record);
```

**Returns:** `Future<RecordMetadata>`

#### `flush()`
Immediately sends all pending batches.

```java
producer.flush();
```

#### `close()`
Flushes remaining records and releases resources.

```java
producer.close();
```

### Interview Notes

- `send()` is **asynchronous** by default.

### Tricky Questions

#### Q1. Is `send()` synchronous?

**Answer:** No. It is asynchronous.

#### Q2. How can we make it synchronous?

```java
producer.send(record).get();
```

> `.get()` waits for acknowledgement.

## Record Metadata

**Metadata** returned after Kafka successfully stores a record.

**Contains:**
- Topic
- Partition
- Offset
- Timestamp

**Example:**
```
Topic     : Orders
Partition : 2
Offset    : 4598
```

```java
RecordMetadata metadata =
    producer.send(record).get();

metadata.partition();
metadata.offset();
```

### Why useful?

- Logging
- Debugging
- Auditing

### Tricky Questions

#### Q1. Does metadata exist before sending?

**Answer:** No. Broker generates it after storing the record.

#### Q2. Is offset generated by the producer?

**Answer:** No. Broker assigns offsets.

## Serialization

**Serialization** converts Java objects into bytes.

> Kafka transports only byte arrays.

```
Order Object → JSON → Bytes
```

### Common serializers

- `StringSerializer`
- `IntegerSerializer`
- `ByteArraySerializer`

Custom serializer also possible.

### Why needed?

Network transfers bytes only.

### Tricky Questions

#### Q1. What happens if producer and consumer use different serializers / deserializers?

**Answer:** The consumer may fail to deserialize the data or read corrupted/incorrect values.

#### Q2. Can Kafka store Java objects directly?

**Answer:** No. Only byte arrays.

---

## Compression

Kafka compresses batches before sending to reduce network usage and storage.

### Supported

| Type | Notes |
|---|---|
| `none` | No compression |
| `gzip` | Good compression, slower |
| `snappy` | Balanced speed and compression |
| `lz4` | Fast |
| `zstd` | Best balance of ratio and speed |

**Example:**
```
100 MB → Compression → 20 MB
```

### Advantages

- Faster network transfer
- Less disk usage
- Higher throughput

### Tricky Questions

#### Q1. Does Kafka compress each record individually?

**Answer:** No. Compression happens at the **batch level**.

#### Q2. Which compression usually provides the best compression ratio?

**Answer:** Generally `zstd` offers the best balance of compression ratio and speed, while `gzip` compresses well but is slower.

---

## Batching

Kafka groups multiple records into one request before sending.

```
Without batching:  100 records → 100 requests
With batching:     100 records → 1 request
```

### Benefits

- Higher throughput
- Lower latency per record
- Fewer network calls

### Tricky Questions

#### Q1. Does batching improve throughput?

**Answer:** Yes. Significantly.

#### Q2. Can batching increase latency?

**Answer:** Yes. Kafka may wait briefly to fill a batch.

---

## linger.ms

Time the producer waits before sending a batch.

**Default:** `0 ms`

**Example:**
```
linger.ms = 10
Kafka waits up to 10 ms for more records before sending.
```

### Trade-off

| Value | Effect |
|---|---|
| Small | Lower latency, smaller batches |
| Large | Better throughput, slightly higher latency |

### Tricky Questions

#### Q1. Will Kafka always wait exactly `linger.ms`?

**Answer:** No. If the batch becomes full earlier, it sends immediately.

#### Q2. Is increasing `linger.ms` always good?

**Answer:** No. It can improve throughput but also increases message latency.

---

## batch.size

Maximum size of one batch (in bytes) for a partition.

**Default:** `16 KB`

If batch reaches the configured size, Kafka sends it immediately.

### Interview Notes

- Measured in **bytes**, not number of messages.
- Separate batches are maintained **per partition**.

### Tricky Questions

#### Q1. Is `batch.size` the number of records?

**Answer:** No. It is the size in **bytes**.

#### Q2. Can multiple partitions share one batch?

**Answer:** No. Each partition has its own batch.

---

## buffer.memory

Total memory available to the producer for buffering unsent records.

**Default:** `32 MB`

If the buffer becomes full, `send()` may block (up to `max.block.ms`) or fail with an exception.

### Why needed?

Absorbs temporary spikes in message production.

### Tricky Questions

#### Q1. What happens if the buffer is full?

**Answer:** The producer blocks temporarily or throws an exception if it cannot obtain memory within the configured timeout.

#### Q2. Does increasing `buffer.memory` increase throughput?

**Answer:** Not necessarily. It mainly allows more buffering; throughput also depends on batching, network, brokers, and acknowledgements.

---

## Retries

Producer automatically retries sending a record when it encounters retriable failures.

### Typical retriable failures

- Temporary network issue
- Leader election
- Broker unavailable

### Why needed?

Improves reliability without requiring application-level retry logic.

### Tricky Questions

#### Q1. Can retries create duplicate messages?

**Answer:** Yes, unless **idempotence** is enabled.

#### Q2. Are all errors retriable?

**Answer:** No. Configuration errors or invalid records are generally not retriable.

---

## Acknowledgements (acks)

`acks` determines how many brokers must acknowledge a write before the producer considers it successful.

| Setting | Behavior | Reliability |
|---|---|---|
| `acks=0` | No acknowledgement | Fastest, least reliable |
| `acks=1` | Leader acknowledges after writing locally | Balanced |
| `acks=all` (or `-1`) | Leader waits for all in-sync replicas (ISR) | Highest reliability |

### Interview Notes

> `acks=all` provides the strongest durability when used with appropriate replication settings.

### Tricky Questions

#### Q1. Which `acks` setting is safest?

**Answer:** `acks=all`.

#### Q2. Does `acks=all` guarantee zero data loss?

**Answer:** No. It greatly reduces the risk, but durability also depends on factors such as ISR configuration (`min.insync.replicas`) and catastrophic failures.

---

## Idempotent Producer

An **idempotent producer** guarantees that retrying the same send does **not** create duplicate records.

**Enable using:**
```properties
enable.idempotence=true
```

Kafka assigns **sequence numbers** to detect duplicates.

### Benefits

- Exactly one copy for retried sends (per partition).
- Safe retries.

### Tricky Questions

#### Q1. Does idempotence work across different producer instances?

**Answer:** No. It applies to a single producer session.

#### Q2. Does idempotence provide transactions across multiple partitions?

**Answer:** No. For atomic writes across partitions or topics, use **Kafka transactions**.

---

## Transactions

Kafka transactions allow multiple records (possibly across multiple partitions/topics) to be committed or aborted as a single **atomic unit**.

```
Write A
Write B
Write C
   ↓
 Commit        Abort
   OR
```

### Why needed?

Prevents partial writes in multi-step operations.

### Tricky Questions

#### Q1. Can transactions span multiple partitions?

**Answer:** Yes.

#### Q2. What happens if a transaction fails before commit?

**Answer:** All records in the transaction are aborted and are not visible to consumers using `read_committed`.

---

## Producer Interceptors

**Producer Interceptors** allow custom logic before records are sent and after acknowledgements are received.

### Examples

- Add headers
- Logging
- Metrics
- Auditing
- Message validation

```
Application → Interceptor → Kafka
```

### Common Methods

| Method | Purpose |
|---|---|
| `onSend()` | Called **before** sending |
| `onAcknowledgement()` | Called **after** broker acknowledgement |
| `close()` | Cleanup resources |

### Tricky Questions

#### Q1. Can an interceptor modify a record before it is sent?

**Answer:** Yes. It can return a modified `ProducerRecord`.

#### Q2. What happens if one interceptor throws an exception?

**Answer:** Kafka catches interceptor exceptions and continues processing, though the interceptor's intended logic may not be applied. Poorly written interceptors can still affect producer behavior, so they should be lightweight and reliable.

## Producer Interview Summary

- ✅ `send()` is **asynchronous** by default.
- ✅ **Sender Thread** performs the actual network I/O.
- ✅ **Serializer** converts objects to bytes.
- ✅ **Partitioner** chooses the destination partition.
- ✅ **Batching** improves throughput.
- ✅ `linger.ms` controls how long to wait for additional records.
- ✅ `batch.size` is measured in **bytes**, not messages.
- ✅ `buffer.memory` stores unsent records temporarily.
- ✅ `acks=all` provides the highest reliability.
- ✅ **Retries** without idempotence can produce duplicates.
- ✅ **Idempotence** prevents duplicate writes caused by retries.
- ✅ **Transactions** provide atomic writes across partitions/topics.
- ✅ **Producer Interceptors** are useful for logging, auditing, metrics, and custom preprocessing.
